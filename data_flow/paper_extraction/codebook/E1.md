## 1. What E1 is asking

**How is the question built?** Structure only — how many statements, how many lists, is there a figure, is there an order to arrange, what kind of thing are the four options.

Never tag what the student must pick (that is E2/format), what NCERT material it rests on (E3), or what the student must think (E4). The single most common E1 error is answering E2's question: "Select the incorrect statement" is about *format*; E1 only cares that the four options are statements.

## 2. Priority order is load-bearing

The script applies 16 patterns in SPEC's stated order, **first match wins**. That order is not cosmetic: an Assertion–Reason question also contains two statements, and a match question also contains lists. Apply the same order by hand:

1. Assertion present → `assertion_reason`
2. "Statement I"/"two statements" without Assertion → `statement_i_ii`
3. Column III / three-column rows → `match_the_lists`
4. List-I/Column-I/"Match" with two lists → `match_the_lists` (but `pair_options` first if the options are single pairs)
5. "correctly/wrongly matched", options are single pairs → `pair_options`
6. arrange / sequence / correct order of events|steps|stages → `arrange_in_order`
7. (increasing|decreasing|correct) order of *a property*, largest-to-smallest → `arrange_in_order`
8. B3 `structure = statements` with combination options → `list_of_statements`
9. reaction arrow **or scheme image** in the stem asking for X/Y/Z/product/reagent/name → `reaction_scheme`
10. the options are images: graphs → `graph_options`; structures → `structure_options`
11. figure with letter labels A–D to identify → `diagram_labelled`
12. figure referred to and needed → `figure_to_read`
13. "____" → `fill_in_blank`
14. "…are respectively" **where the answer has two or more parts** → `multi_part_respectively`
15. the options are full statements to judge → `statement_options`
16. otherwise → `plain_mcq`

**Two labelling conventions (v0.2, confirmed on real papers):**
- A two-statement judge-each item labelled "A"/"B" is `statement_i_ii`, exactly as one labelled "I"/"II". Label style never changes the type.
- A question may legitimately carry **two** E1 tags (e.g. a `fill_in_blank` stem that also requires reading a figure). Record both rather than forcing one. The agent output field holds one value, so put the second in `new_description` as "also figure_to_read" and set `confidence: medium`; this is a real shape the output shape does not cleanly express (see §5).

## 3. The values

### `plain_mcq`
One stem, four short options. The default when nothing else fires.
- **vs `statement_options`:** look at the options. Short values, names or terms → `plain_mcq`. Full prose clauses that each have to be judged true/false → `statement_options`.
- **vs `list_of_statements`:** `plain_mcq` can still *list items inside one sentence*. "How many plants among the following are monocots?" (`2015#130`) is `plain_mcq` — those are items, not lettered statements. This is a SPEC-named boundary and a script self-test.
- **Real example:** `Q-000011` (types of measurement error; four named options).

### `statement_options`
Each option is a full statement to judge.
- **vs `list_of_statements`:** here the statements **are** the options. There are no lettered statements in the stem and no combination options.
- **vs the reaction gap:** four LaTeX chemical reactions are **not** statements. The script explicitly excludes formula/chemical-notation-dominated options for this reason — see §4.
- **Real example:** `Q-000007` — "If ∮ E·dS = 0 over a surface, then:" with four prose claims about flux lines, field magnitude and charge location.

### `list_of_statements`
Lettered statements in the stem; the options are combinations or a count.
- **vs `statement_i_ii`:** three or more lettered statements → `list_of_statements`. Exactly two → `statement_i_ii`.
- **vs `plain_mcq`:** needs *structurally separate* lettered statements (B3's parsed `statements` array), not items inside a sentence.
- **Real example:** `Q-000015` — statements A–D about the female reproductive cycle, options "A and D only" / "A and B only" / "A, B and C only" / "A, C and D only".

### `statement_i_ii`
Exactly two statements; options are true/false combinations.
- **vs `assertion_reason`:** the decisive test is **whether the options ask if one explains the other**, not the labels. Assertion/Reason wording wins (priority 1). Two statements with no because-link are `statement_i_ii`.
- **Real example (SPEC-named):** `2026-May#25` — "Given below are two statements A and B", options "both correct / A correct B incorrect / …". It is `statement_i_ii` **even though the legacy sheet called it Assertion-Reason.** Legacy labels are never evidence here.

### `assertion_reason`
Assertion and Reason given; the options include whether R explains A.
- **vs `statement_i_ii`:** the presence of the word "Assertion" decides it, and it outranks every statement pattern.
- **Warning:** the legacy sheets contain 6 confirmed "Assertion-Reason" rows with no assertion at all. Read the real stem.

### `match_the_lists`
Two lists; options are match codes.
- **vs `match_the_lists`:** count the columns. Three (item · property · group) → `match_the_lists`, and it is checked first.
- **vs `pair_options`:** in `match_the_lists` each option is a *full set* of pairings ("A-ii, B-i, C-iv, D-iii"). In `pair_options` each option is **one** pairing.
- **Note:** match-lists are no longer a Biology-only or 2026-only shape — the 2024 MAIN paper alone is ~10% match-lists across all three subjects.

### `match_the_lists`
Three columns (item, property, group); options are three-part codes.
- **vs `match_the_lists`:** three columns, not two. Checked before `match_the_lists` precisely because the "List-I/Match" wording also appears here.

### `pair_options`
Each option is one pair; pick the correct or the wrong match.
- **vs `match_the_lists`:** one pairing per option versus a full set per option. The script counts separators — a comma or semicolon inside an option means it is a combination, not a single pair.
- **Typical wording:** "which is correctly matched", "which is wrongly matched", "incorrectly paired", "mismatch".

### `arrange_in_order`
Order of events or steps **in time**.
- **vs `arrange_in_order`:** this is the boundary that goes wrong most. Time/stages/steps → `arrange_in_order`. A property (size, energy, acidity, basicity, radius, stability) → `arrange_in_order`.
- **Real example (SPEC-named):** "correct order of organisation of genetic material from largest to smallest" (`2015#161`) is **`arrange_in_order`, not `arrange_in_order`** — the word "order" alone decides nothing. The script's rule 6 is deliberately restricted to `events|steps|stages` so a bare "order of" cannot catch it.
- **Real example of a true one:** PCR's three steps asked as an arrange-in-order item (`2026-May#132`).

### `arrange_in_order`
Order by a property: size, energy, acidity, ionisation enthalpy, bond length.
- **vs `arrange_in_order`:** see above. If the ordering is along a measurable property rather than a timeline, it is this.

### `fill_in_blank`
The stem contains a blank ("____").
- **Note:** up to 18% of the June 2026 Biology paper. It co-occurs readily — a blank plus a needed figure is the standard two-tag case (§2).

### `diagram_labelled`
A figure with letter labels (A–D) to identify.
- **vs `figure_to_read`:** labels to *name* → `diagram_labelled`. A figure whose content must be *used* (a circuit, a graph to read a value off) → `figure_to_read`.
- **vs `graph_options`/`structure_options`:** here the figure is in the **stem**; there the figures are the **options**.

### `figure_to_read`
A figure, circuit or graph is referred to and is needed to answer.
- **vs `reaction_scheme`:** this is the trap the script was fixed for. If the figure is a **reaction scheme** and the ask is for X/Y/Z/product/reagent/name, it is `reaction_scheme`, not `figure_to_read` — even with no text arrow anywhere.
- **Real example of that fix:** `Q-000013` — "Identify product (A) in the following reaction: [structure … undergoing reduction with Zn-Hg and conc. HCl]". The scheme is an image; the first version of `type_patterns.py` mislabelled it `figure_to_read`, losing the fact that it is a reaction question at all and corrupting E2/E3 downstream. Now a regression case in the script's self-test.

### `graph_options`
The options are graphs or figures.
- **Reality check:** this pattern **has never fired on real data**. 162 of 166 scrape files contain zero embedded images, and `option_images` — which is what rule 10 reads — does not exist on any record in this corpus. Note that *stem* figures are now being recovered (real `papers/figures/Q-000002.png`, `Q-000013.png`, 2026-10-12), which reaches rules 11/12, **not** rule 10. `graph_options` and `structure_options` stay unreachable until per-option image crops exist.

### `structure_options`
The options are chemical structures (drawn).
- **vs `statement_options`:** drawn structures, not prose.
- **vs the gap in §4:** drawn *structures* are this. Four *reactions* are not — see §4.

### `reaction_scheme`
A reaction or sequence is shown **in the stem**; identify X/Y/Z, the product, the reagent or the reaction name.
- **The stem is the scope.** This value does not cover "the four options are each a reaction" — see §4.
- **Real example:** `Q-000013` (image scheme, no text arrow); "CH₃CH₂Br + KCN → X; the product X is" (text arrow).

### `multi_part_respectively`
The **answer** has two or more parts given together.
- **Don't tag when (SPEC-named):** the word "respectively" describes the **setup**, not the answer. "…two arms are 5 Ω and R Ω respectively" (`2014#27`) is **not** `multi_part_respectively` — each option there is a single value. The test is always: look at the options, not the stem.

### `list_of_structures` (new in v0.2)
A lettered/numbered list in the stem whose items are **drawn structures or figures** to judge or count — not text statements.
- **vs `list_of_statements`:** `list_of_statements` assumes lettered *text* claims. When the items i–vii are drawn rings ("how many of the following obey Hückel's rule"), it is `list_of_structures`.
- **vs `structure_options`:** here the structures are in the **stem** and the options are a count or a combination; there the structures are the **options**.
- **Provenance:** added 2026-10-09, confirmed on one real 2023 Chemistry question. Narrow and Chemistry-specific.

### `new_type`
Nothing above fits. Give a one-line description in `new_description`. Raises `E_NEW_CATEGORY` (normal) so Stage F sees it. Use it rather than stretching a near value — a stretched value is invisible, a `new_type` is reviewed.

## 4. CONFIRMED GAP — the four options are each a chemical reaction

**This is a real hole in SPEC 13/E1's pattern list, found on real data. It is recorded here, not papered over.**

Real `Q-000005`: *"Which of the following reactions will NOT give primary amine as the product?"* — the four options are each a distinct reagent/arrow transformation (`CH₃CONH₂ → Br₂/KOH`, `CH₃CN → (i) LiAlH₄, (ii) H₃O⁺`, …).

No spec pattern applies:
- rule 9 (`reaction_scheme`) is scoped to a reaction **in the stem**;
- rule 10 (`graph_options`/`structure_options`) covers option **images** only;
- rule 15 (`statement_options`) covers **prose** statements.

The first implementation wrongly claimed `statement_options` — four LaTeX reaction strings each read as a long "statement". **A reaction equation is not a statement to judge.** `scripts/type_patterns.py` now detects this shape (rule 9b) and deliberately returns `None`, which hands the question to the agent — the spec-correct fallback when no pattern decides.

**What the agent should do until the owner decides:** tag `new_type` with `new_description: "the four options are each a chemical reaction"`, `confidence: high`. That makes the shape countable in Stage F instead of hiding it inside `statement_options`.

**Proposal for the owner:** add **`list_of_reactions`** to E1 — "the options are each a chemical reaction to evaluate". It is the exact analogue of `list_of_structures`, which v0.2 already added for the options-are-structures case. `config/allowed_values.yaml` has **not** been changed; this is the owner's call.

A matching gap exists in `answer_form` (E6) for the same question — see `codebook/E6.md` §5.

## 5. Where this draft is genuinely uncertain

1. **The two-tag case has nowhere to go.** SPEC 17.2 says a question may need two E1 tags, but the agent's output shape holds exactly one `question_type`, and `scripts/type_patterns.py` returns exactly one value. §2's workaround (second tag in `new_description`) is my invention, not spec. The owner may prefer a real second field; that would be a schema change, out of this file's scope — and `schemas/E1.json`, which `config/steps.yaml` already points at, **does not exist yet**. **Reported as a build issue.**
2. **`graph_options` / `structure_options` / `list_of_structures` are untested against this corpus.** No real question in the bank can currently reach them. The definitions above are from SPEC and the validation pass, not from a record I could read.
3. **`pair_options` vs `match_the_lists` on five-item lists.** SPEC 2.1 notes real lists that run A–E against I–V. The separator-counting test should still hold, but no real five-item case has been checked.
4. **`confidence` for pattern-decided questions.** When the script decides, no agent runs and no confidence is recorded at all. That is by design, but it means E1's confidence distribution will look artificially sparse in Stage F.

## 6. Proposals for the owner

- **Add `list_of_reactions`** (§4). Highest-value change in this file.
- **Decide how a legitimately two-tag question is stored** (§5.1) — `new_description` is a workaround, not an answer.
- **No other value changes proposed.** ~500 real sampled questions produced only two genuine E1 gaps, and v0.2 already closed one of them (`list_of_structures`).
